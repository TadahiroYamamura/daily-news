# AIエージェント×OAuth 2.0：Device Flowで社内データの安全な認可を実装した話

- URL: https://www.m3tech.blog/entry/2026/07/15/100000
- 収集日: 2026-07-16
- カテゴリ: Security

## 要約

エムスリーの社内レポート認可システムは元々「ブラウザでのSSO・セッションCookie前提」で設計されており、踏み台サーバやコンテナ内シェルなどブラウザを起動できない環境からアクセスできず、Claude Codeのようなエージェントには人間が手動でファイルを渡すしかないという非効率と、セッション全権限をエージェントに渡してしまうリスクが課題でした。この課題に対し、「トークンを使う主体（ブラウザを持たないエージェント）」と「承認する主体（人間）」を分離できるOAuth 2.0のDevice Authorization Grant（Device Flow）が構造的に適合すると判断し、既存のSSO基盤（OIDC IdP）には手を入れず、認可システム自身がAuthorization Serverとなる方針を採用しました。

実装ではまずPhase 1としてWeb画面から手動発行するPAT（個人アクセストークン）を先行リリースして基盤を検証し、その後Device Flowを追加するという段階的なアプローチを取っています。両者はトークンをDBにSHA-256ハッシュのみで保存する不透明トークン方式、GitHub風の用途別プレフィックス付与、Bearer認証ミドルウェアによる検証といった仕組みを完全に共通化し、既存のユーザー/グループ/ロールに基づく認可判定ロジックには一切手を加えないことで、権限逸脱を構造的に防いでいます。Device Flowのシーケンスは、CLIが`/device/code`でdevice_code/user_codeペアを取得し、ユーザーがブラウザでuser_codeを入力して承認、CLIが`/device/token`をポーリングしてトークンを受け取るという標準的な流れで、既存のnginxのauth_requestにも1行追加のみで対応できた点が実装コストの低さを示しています。

得られた知見として、IdP自体に変更を加えずともCLI/エージェント対応が実現できること、既存の認可ロジックを再利用することで安全性を担保しつつ開発コストを抑えられることが挙げられており、この手法は他の内製システムをCLI・エージェント対応させる際にも再利用可能なモデルとして位置づけられています。
