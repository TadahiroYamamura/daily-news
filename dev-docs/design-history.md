# 設計の経緯と今後の改善計画

このリポジトリの設計は、個々のコミットログ(Why)だけでは追いにくい大きな方向転換を何度か経ている。その経緯と、まだ着手していない今後の改善計画をここにまとめる。個々の変更の詳細な理由は`git log`を参照。

## 主要な方向転換の経緯

1. **Claude Tag(Claude in Slack)は使えない** — Slack内で双方向にやり取りする理想形はTeam/Enterpriseプラン限定の機能で実現できるが、ユーザーの契約プラン(Pro/Max)では使えないと判明。自前で何かを作る前提に転換した。
2. **自前Slack Bot案を却下** — Bolt + Socket ModeでSlack Bot常駐を検討したが、Slackのスレッドは1階層しかなく、「記事ごとのスレッド」を`thread_ts`で安全にマッピングする実装が複雑になることが判明。ヘッダーメッセージへの返信として記事を投稿する当初案はSlackの仕様上成立しないことも発覚した。
3. **VPS + カスタムWebアプリ案を却下** — ConoHa VPSを契約し、Slack Incoming Webhook通知+FastifyのWebアプリで深掘りを提供する構成を一度は詳細設計したが、「この端末(Linux、ほぼ常時稼働)でも`/loop`が使えるか」という問いをきっかけに再検討。公式ドキュメントで、Remote Control機能を使えばこの端末で動き続けるClaude Codeセッションにスマホから直接双方向で接続できることが確認できたため、VPS・カスタムアプリ・Slack連携を丸ごと不要にできると判断した。
4. **GitHub Pages(HTML生成)も過剰と判断** — 当初はGitHub Pages向けにJSON→HTMLを生成する`render_digest.py`を実装したが、実際に86件のダイジェストを生成してみたところ、この程度の一覧表示にHTML化・専用サイト配信は過剰と判断。GitHubの標準ブラウザ表示でそのまま読めるMarkdown生成に置き換え、`docs/`ディレクトリとGitHub Pages設定を丸ごと廃止した。
5. **Reddit収集をLobstersに置き換え** — `old.reddit.com`のJSON APIが、家庭用ISP(実機のSoftBank回線)経由でも`403 blocked by network security`で安定してブロックされることを実機検証で確認。ブラウザ風ヘッダーを付けても回避できず、UA偽装では解決しない構造的な問題と判断し、同種のコミュニティ投票型SNSであるLobstersに切り替えた。あわせて日本語圏のエンジニア向けソースとしてZenn・Qiitaを追加した。
6. **データ取得はAPI/RSS/Atomの決定論的パースに統一** — はてなブックマークとHacker NewsはもともとWebFetchでページをLLMに読ませて抽出させていたが、実行のたびに結果がブレるリスクがあった。全ソースを構造化データ(はてなRSSの`hatena:bookmarkcount`、HN Firebase API、Lobsters JSON API、Zenn/Qiitaのフィード)から決定論的に取得する方式に統一し、LLMの役割を翻訳・興味度評価・深掘り要約に限定した。
7. **Markdownファイルをやめ、GitHub Issueのチェックボックスに一本化** — `digests/YYYY-MM-DD.md`をGitHubのブラウザ表示で読む方式にしていたが、「気になった記事をタップでチェックして選別したい」という要望を実現しようとしたところ、GitHubのMarkdownチェックボックスは通常のリポジトリファイル(blobビュー)ではクリックできず、Issue/PR本文でのみタップでトグルできる仕様であることが判明。`digests/*.md`の生成を廃止し、`digest`ラベル付きのGitHub Issueとして投稿する形式に切り替えた。深掘り対象の特定は、Issue本文に埋め込んだ`<!-- id:... -->`コメント(表示はされない)を`parse_checked_ids()`で読み取ることで行う。

## 今後の改善計画

### 運用の頑健化

- `/loop`の7日失効を見落とさないための運用ルール化(現状はカレンダーリマインダー等、ユーザー側の手動運用に依存している)
- `render_digest.py`の異常系(欠損フィールド、特殊文字)のテスト強化
- 深掘り→アーカイブの流れ(現状は`README.md`の規約をClaudeが都度読んで従う運用)を専用スキル化するかの検討

### 興味プロファイルの学習ループ(未着手、意図的に見送り中)

アーカイブ(`archive/`)の蓄積からカテゴリ/キーワードの重み付けを学習し、`PROFILE.md`に反映する仕組み。**現時点では意図的に着手していない**。理由:

1. 運用開始直後は学習に十分なデータがなく効果測定できない
2. 学習ロジック自体のテスト観点も、運用データが溜まるまで定義しづらい
3. まずは手動で`PROFILE.md`を編集する運用を数週間回し、「本当に学習が必要か」「どのシグナルが有効か」を人間が観察してから自動化する方がリスクが低い

着手する場合も自動反映はせず、月次で「`PROFILE.md`への追記案」を人手でレビューする程度に留める想定。
